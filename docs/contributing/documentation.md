# Documentation system

## Overview

The user-facing pages under `docs/products/` and `docs/references/` are generated by [**saifdocs**](https://github.com/safe-ai-factory/saifdocs) from a declarative `docspec/` tree.

Saifdocs is our own LLM-driven docs generator — it reads `docspec/` and uses an agent to produce the actual markdown pages in `docs/`. This allows us to have consistent styling and tone.

The one rule that follows from this:

`docs/products/` and `docs/references/` are **generated** from `docspec/`. Do not edit them directly — your changes will be overwritten on the next regen. To change a user-facing page, edit the corresponding `docspec/` source.

Everything else under `docs/` (`docs/README.md`, `docs/contributing/`, anything you add at the top level of `docs/`) is **handwritten** and not touched by saifdocs. Edit those directly.

| Path                      | Owner                | Edit how                            |
| ------------------------- | -------------------- | ----------------------------------- |
| `docs/products/saifctl/`  | saifdocs (generated) | Edit `docspec/products/saifctl/`    |
| `docs/references/`        | saifdocs (generated) | Edit `docspec/references/`          |
| `docs/contributing/`      | handwritten          | Edit the file directly              |
| `docs/README.md`          | handwritten          | Edit the file directly              |
| Any other top-level `docs/` file | handwritten   | Edit the file directly              |

When you run `saifdocs clear`, it only deletes paths listed in `docspec/.manifest.json`, so handwritten files at `docs/contributing/` and `docs/README.md` survive a full regen.

### Where does X go?

| Kind                                                       | Goes to                                                              | Notes                                                          |
| ---------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------- |
| User-facing concepts<br/> (what something is, how it works)      | `docspec/products/<product>/concepts/<slug>.md`                      |                                                                |
| User-facing how-tos<br/> (solve problem)             | `docspec/products/<product>/how-tos/<slug>.md`                       |                                                                |
| User-facing tutorials<br/>(learning journey)         | `docspec/products/<product>/tutorials/<slug>.md`                     |                                                                |
| CLI command, API method, or config field reference         | `docspec/references/.../<slug>.md` | With `source:` pointer at the implementation file.          |
| Internal architecture, dev-loop walkthroughs | `docs/contributing/architecture/<slug>.md` (or `docs/contributing/<slug>.md`) | Handwritten. No docspec, no manifest.                |
| Image, diagram, or other binary asset                      | `docspec/assets/<filename>`                                          | Reference from a docspec body via instruction text (saifdocs#1 pending). |

## Authoring

How to write the source files that the system reads. For docspec/ entries (user-facing), that means frontmatter shapes and the `source:` pointer pattern. For `docs/contributing/` (handwritten), that means knowing what lives there. The style guide at the end applies to both.

### docspec/ tree

`docspec/` is the input [**saifdocs**](https://github.com/safe-ai-factory/saifdocs) reads. Its layout is shaped by [Diátaxis](https://diataxis.fr): one directory per quadrant (concepts, references, how-tos, tutorials), so where a file lives already declares what kind of doc it is. Every entry has YAML frontmatter that matches the schema for its quadrant — saifdocs validates this on every gen run.

```
docspec/
├── products/
│   └── saifctl/
│       ├── product.md              (landing-page intent)
│       ├── concepts/               (Diátaxis: understanding)
│       ├── how-tos/                (Diátaxis: task-driven)
│       ├── tutorials/              (Diátaxis: learning-driven)
│       └── personas/               (audience definitions)
├── references/                     (Diátaxis: information)
│   ├── commands/
│   ├── agents/
│   ├── designers/
│   ├── indexers/
│   ├── config.md
│   ├── env-vars.md
│   ├── ...
├── personas/                       (cross-product personas)
├── tasks/                          (audience tasks for how-to framing)
├── templates/pages/                (page-shape intent prompts)
├── assets/                         (images / diagrams)
├── rules.md                        (global style: be concise, lead with outcome)
└── .manifest.json                  (committed; what each entry generates to)
```

### Frontmatter schemas

Every docspec entry has a YAML frontmatter block. The schema is defined in `vendor/saifdocs/src/docspec/schema.ts` — that file is the source of truth. Cheat-sheet:

#### Concept (`docspec/products/<p>/concepts/*.md`)

```yaml
---
id: leash-access-control          # kebab-case slug
explains: how Cedar policies and the Leash sidecar enforce filesystem and network rules at runtime
learning_outcomes:
  - The two pieces of Leash (Cedar policy + eBPF enforcement) and how they compose.
  - "When Cedar's permit-by-default is appropriate vs. the bundled `deny-network.cedar`."
  - The override surface (--cedar flag, dangerousNoLeash escape hatch).
analogies:
  - "Cedar is the policy language; Leash is the bouncer reading the policy at the door."
---
```

#### Reference (`docspec/references/**/*.md`)

```yaml
---
source: src/cli/commands/run.ts   # path the agent will read at gen time
type: cli-command                 # enum: cli-command | api-method | config-schema
---
```

The reference body comes from the agent reading `source:`. **Do not hand-write the body** — write the frontmatter and any intent paragraph, and let saifdocs generate the rest. If the body drifts from code, fix the code or the surrounding intent, not the body.

#### How-to (`docspec/products/<p>/how-tos/*.md`)

```yaml
---
id: split-feature-into-phases     # optional; defaults to filename stem
persona: feature-author
tasks:
  - phase-a-large-feature
goal: "Split a large feature into phases so each phase passes the gauntlet independently."
---
```

#### Tutorial (`docspec/products/<p>/tutorials/*.md`)

```yaml
---
id: spec-driven-development
persona: new-user
prereq_concepts: [features, gate-reviewer-holdout]
learns_concepts: [feature-lifecycle, feat-run-loop]
goal: "Build a small feature end-to-end with `saifctl feat design` and `saifctl feat run`."
---
```

Tutorials may have a sibling `tutorials/index.yaml` to declare ordering and prereq chains.

#### Task (`docspec/tasks/*.md`)

```yaml
---
prereq_concepts: [features]
arrival_context: search           # enum: search | readme | docs-link | error-message
search_terms: ["how to phase a feature", "phased run"]
user_stage: getting-started       # enum: evaluating | getting-started | established
---
```

#### Page template (`docspec/templates/pages/*.md`)

```yaml
---
intent: Goal-oriented how-to; reader wants the fastest path to a working command and clear safety boundaries.
---
```

#### YAML gotchas

- List items containing `: ` or starting with backticks must be quoted. `- "When Cedar's permit-by-default is appropriate"` not `- When Cedar's permit-by-default is appropriate`.
- The `type:` field on references is a **closed enum** — `cli-command | api-method | config-schema` only. Custom categories are tracked at [saifdocs#1](https://github.com/safe-ai-factory/saifdocs/issues/1); until that lands, pick the closest enum value.

### The `source:` pointer pattern (references only)

A reference entry's body is generated by the agent reading the file at `source:` and writing a doc that summarizes the implementation. You write:

1. The frontmatter (`source`, `type`).
2. Optionally, an intent paragraph above any subheadings, framing what the reference should emphasize.

You do **not** write the prose body — the agent writes it from the source file. This means:

- If a CLI flag changes in `src/cli/commands/run.ts`, the reference body updates the next time the entry is regenerated. No manual sync.
- If the body is wrong, the fix is usually to clarify the source file's comments or restructure the code, not to edit `docs/references/`.
- If you need a category outside the enum, pick the closest match and track the gap on saifdocs#1.

### docs/contributing/ subtree

Handwritten. No docspec involvement. Two kinds of content live here:

- **Topical contributor notes** at `docs/contributing/<slug>.md` — adding a new agent profile, options bridging, the inner-round stats format, branding, etc.
- **Architecture deep-dives** at `docs/contributing/architecture/` — eleven docs covering Cedar/Leash, the orchestrator, sandbox isolation, gate/reviewer, test runner, spec pipeline, extension points, services and IaC, etc. Plus a `README.md` index.

Cross-link convention: when a contributor doc points into source, use `path/to/file.ts:42` so the link resolves to a specific line in editors that follow `:N` anchors.

### Style guide

- Lead with the concrete thing — the outcome, the file, the function, the command — before any abstract framing of why it matters.
- No meta-narration: skip "this section explains…" / "this document covers…" preambles. The heading already says it.
- Plain language; introduce a necessary term once, then use it.
- Be dense. Cut filler.

Source of truth: [`docspec/rules.md`](../../docspec/rules.md).

## Regeneration pipeline

How a docspec change becomes a generated `docs/` page, and the gates that watch the pipeline. Read this when you've edited a docspec entry and need to ship it, or when CI complains about a stale manifest.

### saifdocs CLI

Six commands. Run from the saifctl project root.

| Command                  | Purpose                                                        | When to run                                          |
| ------------------------ | -------------------------------------------------------------- | ---------------------------------------------------- |
| `saifdocs gen`           | Read docspec, build manifest, emit a saifctl feature tree.     | Before a regen; `saifctl feat run` then writes docs. |
| `saifdocs gen --dry-run` | Build and write the manifest only; no LLM, no feature tree.    | Local validation, CI.                                |
| `saifdocs update`        | Regenerate a single entry's output.                            | One file changed, full regen overkill.               |
| `saifdocs validate`      | Schema-only check (no source-of-truth comparison).             | Quick frontmatter pass.                              |
| `saifdocs audit`         | Coverage / drift report against generated output.              | Sanity check after a regen.                          |
| `saifdocs clear`         | Delete manifest-tracked files only. Leaves handwritten alone.  | Before a clean regen.                                |
| `saifdocs review`        | LLM review of generated content against docspec intent.        | After a regen if quality is in question.             |

The local saifdocs is vendored at `vendor/saifdocs/` (git submodule) and also published as `@safe-ai-factory/saifdocs` on npm. CI uses the vendored copy.

### End-to-end pipeline

```
docspec/                              you edit
   │
   │  saifdocs gen --project-dir .
   ▼
docspec/.manifest.json                committed; tracks every output path
   +
saifctl/features/saifdocs-<ts>/       feature tree, one phase per file
   │
   │  saifctl feat run --feature saifdocs-<ts>
   ▼
docs/products/, docs/references/      generated; do not hand-edit
```

A full regen needs LLM credentials and Docker (saifctl runs the agent in a container). `--dry-run` skips both.

`docspec/.manifest.json` is committed to git. CI fails if it's stale relative to docspec sources. After any structural docspec change (new entry, renamed entry, deleted entry, frontmatter type change), run `saifdocs gen --project-dir . --dry-run` and commit the manifest.

### Running a regen

```bash
# from the repo root, with LLM credentials and Docker available:
npx -y @safe-ai-factory/saifdocs@latest gen --project-dir .
saifctl feat run --feature saifdocs-<timestamp>
```

The first command emits a saifctl feature tree; the second drives an agent through it. See the [saifdocs README](https://github.com/safe-ai-factory/saifdocs) for full options.

### Web sync

```
docs/                       in saifctl repo
   +
docspec/.manifest.json
   │
   │  web/scripts/sync-docs.ts
   ▼
web/src/content/docs/       in safeaifactory.com repo
   │
   │  publish-web.yml on push to main
   ▼
safeaifactory.com           live site
```

`web/scripts/sync-docs.ts` pulls from three sources: `saifctl` (this repo's `docs/` + `docspec/.manifest.json`), `saifbox` (vendored), and `saifdocs` (vendored). Section ordering on the site is fixed: landing → tutorials → how-tos → concepts → references.

The `docs/contributing/` subtree is not synced — it stays in-repo for contributor reference only.

### CI gate

`.github/workflows/tests-docs.yml` triggers on PRs touching `docspec/`, `docs/`, or any source file referenced by a `source:` pointer (`src/cli/commands/`, `src/agent-profiles/`, `src/config/`, etc.). The full path list is in the workflow file.

What it runs:

1. `node vendor/saifdocs/dist/cli.js gen --project-dir . --dry-run` — schema validation, frontmatter checks, source-pointer existence.
2. `git diff --exit-code docspec/.manifest.json` — fails if the committed manifest doesn't match what `--dry-run` produced.

Once a full saifdocs run has populated `docs/`, the dry-run check will be replaced by `saifdocs validate` for full staleness comparison (TODO at the bottom of the workflow file).

## Cookbook

Recipes for common tasks, and the mistakes we keep seeing. If you only read one section before editing, read the mistakes list.

### Common workflows

#### Add a new CLI command doc

1. Implement the command at `src/cli/commands/<name>.ts`.
2. Create `docspec/references/commands/<name>.md` with frontmatter:
   ```yaml
   ---
   source: src/cli/commands/<name>.ts
   type: cli-command
   ---
   ```
3. Optionally add an intent paragraph below the frontmatter.
4. Run `saifdocs gen --project-dir . --dry-run` to update the manifest.
5. Commit both the new docspec entry and the updated `docspec/.manifest.json`.
6. The next full regen (`saifdocs gen` + `saifctl feat run`) writes `docs/references/commands/<name>.md`.

#### Update an existing concept

1. Edit `docspec/products/saifctl/concepts/<slug>.md` (frontmatter and/or body).
2. Either run `saifdocs update <path>` for a single-entry regen, or wait for the next full run.
3. If you changed structure (frontmatter shape, file rename), run `saifdocs gen --dry-run` and commit the manifest.
4. Commit both the docspec source and the regenerated `docs/...` output.

#### Add a contributor architecture note

1. Write `docs/contributing/architecture/<slug>.md` directly.
2. Add a row to `docs/contributing/architecture/README.md`.
3. No docspec, no manifest. The next saifdocs regen leaves your file alone.

#### Add an asset

1. Put the file at `docspec/assets/<filename>`.
2. From a docspec body, reference it via instruction text ("Embed `assets/foo.png` here as a diagram of …"). The agent will write the markdown image syntax.
3. Direct embedding from frontmatter is tracked at saifdocs#1.

#### Replace a reference's `type:` enum value

The enum is `cli-command | api-method | config-schema`. If your reference doesn't fit, pick the closest, leave a comment in the entry intent paragraph, and add a note to saifdocs#1.

### Common agent mistakes

In rough order of how often they actually happen:

1. **Editing `docs/products/` or `docs/references/` directly.** Changes get overwritten on next regen. Edit `docspec/` instead.
2. **Hand-writing reference bodies.** The body is generated from `source:`. Edit the source file's comments/structure if the body is wrong.
3. **Inventing a `type:` value.** It's a closed enum. See saifdocs#1.
4. **Forgetting to commit `.manifest.json`.** CI fails. After any docspec structural change, run `saifdocs gen --dry-run` and commit the manifest.
5. **Putting internal architecture under `docspec/`.** Architecture docs are handwritten contributor content; they live at `docs/contributing/architecture/`, never in docspec.
6. **Confusing how-tos with concepts.** A how-to has `goal:` and a sequence of steps; a concept has `learning_outcomes:` and explains a model. If unsure, ask: "does the reader want to *do* a specific thing right now?" — yes → how-to, no → concept.
7. **Missing YAML quotes** on list items containing `: ` or starting with backticks. js-yaml will reject the entry.
8. **Running `saifdocs clear` and panicking** when generated docs vanish. They're meant to. The handwritten subtree (`docs/contributing/`, `docs/README.md`) is intact.
9. **Editing `vendor/saifdocs/` to fix a docspec issue.** That's a saifdocs change — bump saifdocs separately, file an issue at the saifdocs repo if needed.
