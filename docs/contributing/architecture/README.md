## Reading paths

Common tasks → which files in what order:

- **"I'm new to saifctl, what do I read?"** → `orchestrator.md` → `sandbox-isolation.md` → `gate-and-reviewer.md`. The other eight specialize.
- **"I'm adding a new agent CLI"** → [`../adding-agents.md`](../adding-agents.md) (practical) → `extension-points.md` (contract) → `installation-scripts.md` (`agent.sh` lifecycle).
- **"I'm debugging why a test runner can't reach staging"** → `test-runner.md` (sidecar protocol) → `services-and-iac.md` (network setup) → `installation-scripts.md` (`stage.sh`).
- **"I'm reviewing a security-relevant change"** → `security-threats.md` (audit map) → relevant subsystem doc.
- **"I'm extending Cedar policies"** → `cedar-and-leash.md` → `security-threats.md` (#2, #6 — what the existing forbids defend against).
- **"I'm touching anything in `src/orchestrator/`"** → `orchestrator.md` first; check the relevant linked subsystem.

## Conventions used in these docs

- **File:line anchors** to `src/` so claims are verifiable. If a claim is wrong, the anchor shows where to fix.
- **Concrete first.** Each section opens with the artefact (file path, function name, command), not the rationale.
- **Tables for enumerations.** When 3+ things are being listed, they're in a table.
- **Cross-links over duplication.** Each subsystem doc covers its own concern; cross-links into others where relevant. Reading two docs end-to-end shouldn't double-cover the same material.
- **Style rules** for new contributor docs are pinned in user memory ("Internal contributor docs — concrete first, no meta-narration"). Same rules apply when expanding any of these files.
